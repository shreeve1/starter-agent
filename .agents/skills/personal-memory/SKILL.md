# Personal Memory

Use this skill to operate the local `memory/` workspace memory system. This memory is for non-code preferences and durable personal context, not application source knowledge.

## Scope

Memory lives in `memory/` at the workspace root.

Populated memory `.md` files are tracked in the workspace's local git repo. Keep the repo without a remote and never push. Shipped hooks are optional and are disabled in this Codex workspace; run the audit directly before committing. Never store credentials (git history keeps them). Binaries and `memory/raw/` stay git-ignored.

## Safety Rules

- Never store secrets, tokens, passwords, API keys, bearer strings, OAuth credentials, or credential-like config. Omit them automatically, note the omission in the `memory/log.md` entry, and never ask.
- Client and third-party information (client names, environments, contacts, config facts) IS allowed — it is what makes memory useful. Only credentials are excluded. Exception: Ticket Guides in `memory/guides/` keep their redaction rules (no client names, user emails, hostnames, IPs, tenant IDs, raw logs, or full ticket text).
- Prefer short summaries over raw content. Do not store full emails, screenshots, client documents, or transcripts by default.
- Use `memory/raw/` only when the user explicitly asks to keep raw material.
- Strip credentials from anything written, including raw material.

## Data Classes

- `shareable-scaffold`: rules, templates, and empty folder placeholders.
- `personal-summary`: locally tracked summaries of preferences, docs, workflows, communication style, and client facts.
- `raw-private`: git-ignored raw snippets, attachments and binaries. Use only with explicit approval.

## Directory Contract

```text
memory/
├── README.md
├── TEMPLATES.md
├── index.md
├── log.md
├── glossary.md           # entity directory (shorthand -> identity)
├── preferences/
├── docs/
├── voice/
├── email/
├── guides/               # redacted Ticket Guides
├── workflows/<topic>/    # promoted workflows by topic; index.md generated by indexes.py
├── decisions/<topic>/    # promoted decisions by topic; index.md generated by indexes.py
├── clients/              # Client Memory: clients/<subject>/<short>/<slug>.md
│   └── _hubs/            # generated by hubs.py; never hand-edited
├── candidates/           # not audited
└── raw/                  # git-ignored; explicit approval only
```

## Memory Read Policy

Use tiered reads:

1. At session start or first workspace-specific task, read `memory/index.md` and `memory/glossary.md`, enumerate the `memory/preferences/` directory (including hidden files), then read every `.md` file listed. Use available file tools or, in Codex PowerShell, `Get-ChildItem -LiteralPath memory/preferences -Force` and `Get-Content -LiteralPath`; no tool named `read` is required. Skip any that do not exist. Read `CONTEXT.md` before ticket, project, research, scope, or memory work, and whenever the user's wording sounds like a defined term.
2. Treat index rows as pointers, not facts: open the linked file before relying on or acting on a row. Use `memory/glossary.md` to resolve shorthand entities (client short names, nicknames, acronyms, project/engagement codenames) to full identity.
3. Read promoted memory files relevant to the task before choosing tools, applying workflow rules, drafting user-facing communication, or acting on workspace-specific behavior.
4. Before writing email, voice scripts, Slack messages, reports, or user-facing communication, check relevant promoted memory under `memory/email/`, `memory/voice/`, or `memory/preferences/`.
5. Before working on a client's ticket, project or meeting, read its hub `memory/clients/_hubs/<short>.md` and open the notes relevant to the task. Client skills read Client Memory through the hub, never by guessing note paths.
6. Before researching a ticket, check the Procedures that could fit the ticket in every area (Shared in `memory/workflows/*/` with `type: procedure`, then the client's in `clients/<short>/procedures/*/`) and then the relevant redacted Ticket Guides under `memory/guides/`, after fetching the ticket and before web research.
7. Before wrapping up, run the end-of-session aggregation (see Global Capture).

If `memory/index.md` does not exist, proceed normally and create it only when writing the first promoted memory item.

Read tolerantly. Never refuse to use a memory file because of missing optional frontmatter fields, an unknown `type`, extra unrecognized keys, a missing `index.md`, or a broken cross-link. Do best-effort consumption; a broken link may just be not-yet-written memory.

## Cross-linking

Memory topics may reference each other with standard markdown links.

- Use workspace-relative paths starting with `memory/`, for example `[email tone](memory/email/tone-and-format.md)` — the same base `memory/index.md` uses.
- A link asserts a relationship; the kind lives in the surrounding prose. Add related links under a `## Related` heading when a topic depends on, supersedes, or informs another.
- When promoting, if the new topic clearly relates to an existing one, add a cross-link in the `## Related` section instead of duplicating content.
- Backlinks ("Cited by") are not stored in files. Compute them at read time by reversing the link graph when it aids retrieval.

## No Candidates

There are no memory candidates and no approval step for memory writes (a `memory/candidates/` folder, if present, is not part of this system and is not audited). Memory is written autonomously when a capture trigger fires. The guards are checks, not questions: the Safety Rules, the Conflict Resolution rule (supersede, never silently overwrite), the grounding rule, and `gate.py audit`.

## Setup Workflow

Use when setting up this memory system in a workspace.

1. Create directories:
   - `memory/preferences/`
   - `memory/docs/`
   - `memory/voice/`
   - `memory/email/`
   - `memory/guides/`
   - `memory/workflows/<topic>/` and `memory/decisions/<topic>/` — one folder per topic in the `topics` list of `memory/schema.json` (a new topic only with the owner's OK)
   - `memory/clients/`
   - `memory/raw/`
2. Create committed scaffold files if missing:
   - `memory/README.md`
   - `memory/TEMPLATES.md`
   - `.gitkeep` in each memory subdirectory.
3. Add or update `.gitignore` so `memory/raw/` and binaries are ignored while memory `.md` files are tracked; make sure the repo has no remote. Configure hooks only when the owner separately requests it; otherwise audit directly and never push.
4. Add or update `AGENTS.md` with the personal memory rules.
5. Do not create populated `memory/index.md` or `memory/log.md` until the first capture or promotion.
6. Verify paths exist and report changed files.

## Naming Conventions

Use lowercase hyphenated slugs. Default promoted topic files:

- `memory/preferences/assistant-style.md`
- `memory/email/tone-and-format.md`
- `memory/voice/voice-mode.md`
- `memory/docs/important-docs.md`
- `memory/workflows/<topic>/<slug>.md` (e.g. `memory/workflows/memory/session-end.md`)
- `memory/decisions/<topic>/decision-<slug>.md`
- `memory/guides/<product>-<problem>.md`
- `memory/glossary.md` (single file; sections People / Acronyms / Codenames)
- `memory/clients/<subject>/<short>/<slug>.md` (Client Memory)

Workflows and decisions live in topic folders; no promoted file sits directly in `workflows/` or `decisions/`. Pick a topic from the `topics` list in `memory/schema.json` (a new topic only with the owner's OK) — then after writing run `python3 .agents/skills/personal-memory/indexes.py` and `gate.py audit`. 15-file rule: a memory folder holding more than 15 `.md` files directly gets topic subfolders plus a generated index; `gate.py crowded` reports it.

## Global Capture

Watch for capture triggers in every meaningful session, not only when the user says "remember this." Check for them once, at the end of each task:

- The user corrects you or overrides something you did.
- The user states a rule or preference about how to work ("always…," "never…," "we use X for Y," "keep it to…").
- The user describes how a process or workflow goes, or sets a boundary on one.
- A decision is settled that a future session would otherwise re-litigate.
- You discover a non-obvious fact likely to come up again (a fix, a gotcha, a tool quirk, how their stack or a client's environment is set up) that a future session could not cheaply rediscover.

Write everything that qualifies once, at the end of the task, per the Capture Workflow below — not mid-task after each trigger. Do NOT ask first and do NOT append an "ask to remember" footnote.

End-of-session sweep: before wrapping up meaningful work, capture what qualifies, then give the report (see Output Rules). If nothing qualified, say: `Memory check: nothing worth capturing.`

Do not capture one-off task details (a single ticket, user, record, or device), the status of work still in motion (save it once, when it settles), temporary instructions, facts memory already states correctly, guesses about personality, or credentials.

Exceptions:

- `clients/<short>/tickets/`, `clients/<short>/projects/`, `clients/<short>/meetings/` and `clients/<short>/procedures/` (workspace root) are documents, not memory. The one-off / work-in-motion exclusion does not apply to them. Lasting facts found there still get copied into Client Memory.
- Temperature carve-out: a dated, sourced observation of what pleased or frustrated a client (for example "2026-10-07, #70474: asked for fewer status emails") goes to `memory/clients/temperature/<short>/`. A character judgement ("Ed is impatient") is still a personality guess and is never stored.

## Capture Workflow

Runs autonomously at the end of each task. It never asks the user. Only ask when the user's own request is ambiguous about what to do, never to get permission to write memory.

Grounding: write only what the session actually showed (tool output, file contents, or the user's own words). Do not store guesses. If a fact is plausible but not observed, either omit it or mark it `unverified` in Notes.

Omit automatically (note the omission in the log entry, never ask):

- Credentials of any kind (see Safety Rules).
- Raw material the user did not explicitly ask to keep.
- Ticket Guides: never auto-write to `memory/guides/`. Otherwise route a guide-shaped item to `memory/workflows/<topic>/` or `memory/docs/` as a redacted note.

If the target file is unclear, pick the closest existing topic file by `memory/index.md` row and note the choice in the log entry. Do not store a rule you cannot place.

Direct promotion steps:

1. Read `memory/index.md` if it exists.
2. Read only promoted topic files needed to detect conflicts or merge into the right category.
3. Write or update the appropriate promoted topic file under:
   - `memory/preferences/`
   - `memory/docs/`
   - `memory/voice/`
   - `memory/email/`
   - `memory/guides/` — never auto-written here.
   - `memory/workflows/<topic>/<slug>.md` — pick a topic from the `topics` list in `memory/schema.json` (a new topic only with the owner's OK). Shared Procedures (`type: procedure`) here are written only through an owner-approved change, never auto-captured. After writing, run `indexes.py` and `gate.py audit`.
   - `memory/decisions/<topic>/decision-<slug>.md` — same topic list; after writing, run `indexes.py` and `gate.py audit`.
   - `memory/clients/<subject>/<short>/<slug>.md` — Client Memory, for lasting facts about one client. See Client Memory below. After writing, run `python3 .agents/skills/personal-memory/hubs.py`; add an `index.md` row under `## Client Hubs` for any new hub.
   - `memory/glossary.md` — entity directory (shorthand -> identity). Route here for plain label expansions; contested/overloaded terms go to `CONTEXT.md` instead. When first created it gets its OWN `index.md` row for discoverability; `gate.py audit` audits promoted folders and Client Memory, not root files, so it will not flag a missing glossary row. Internal format: see the `glossary.md` template in `memory/TEMPLATES.md`.
4. Update frontmatter to `status: promoted` where relevant.
5. Create or update `memory/index.md` with the promoted row. Carry the file path either backticked (`` `memory/decisions/<topic>/decision-x.md` ``) or as a markdown link (`[title](memory/decisions/<topic>/decision-x.md)`) so `gate.py audit` can recognize the entry.
6. Create or update `memory/log.md` with a promotion entry.
7. Run `python3 .agents/skills/personal-memory/indexes.py` (regenerates the two topic sub-indexes; skip if no workflow/decision changed), then `python3 .agents/skills/personal-memory/gate.py --memory memory audit`. If audit fails, apply the safe deterministic fixes from Lint Workflow (add missing index rows, remove stale rows, fix topic placement), then re-run until it exits 0.
8. Report per Output Rules.

## Client Memory

Lasting client facts live at `memory/clients/<subject>/<short>/<slug>.md`, one fact per note, template in `memory/TEMPLATES.md`. `<short>` is the Client Short Name from `memory/glossary.md` (add the client there first if missing). Required frontmatter: `type: client-memory`, `client`, `subject`, `title`, `verified` (YYYY-MM-DD last confirmed), `source` (ticket `"#70358"`, `"the owner said"`, or `"meeting <session8>"`).

Subjects come from the `client_subjects` list in `memory/schema.json` — the source of truth. An agent adds a subject only with the owner's approval, and `gate.py audit` fails any note whose subject is not in the schema. What a subject holds, e.g.: `halo` — the client's ticket system setup (client ID, contracts, ticket habits, sites); `365` — Microsoft 365 / Entra / Exchange tenant facts; `temperature` — dated, sourced observations of what pleases or frustrates the client (never personality guesses).

A fact spanning subjects is filed where a task would look first and linked (by `memory/...` path) from a short note in the other subject.

Hubs: `python3 .agents/skills/personal-memory/hubs.py` regenerates `memory/clients/_hubs/<short>.md` for every client found under any subject (notes by subject with verified date, plus that client's `clients/<short>/tickets/`, `projects/` and `procedures/` files). Never edit hubs by hand. `hubs.py --check` exits 1 if a hub is out of date. Only the main session writes Client Memory and runs `hubs.py`; subagents return facts.

## Conflict Resolution

- A new item that contradicts an existing promoted rule supersedes it automatically.
- Update the promoted topic file: make the new rule active and record the prior rule under `## Notes` as `Superseded YYYY-MM-DD: <old rule>`. Never silently delete the old rule. Exception: Procedures are corrected in place; git is the history.
- If the two rules could both hold (different scope or client), keep both and note the scope that separates them.
- Record the supersession in `memory/log.md`.

## Recovery Workflow

Scaffold or personal files may be missing in a fresh copy or teammate
workspace. Before writing any promoted memory in a run, ensure the scaffold
exists first, then recover the personal files:

- If `memory/README.md` or `memory/TEMPLATES.md` is missing, recreate it — it is
  scaffold, not personal state. Restore `README.md` as the memory
  contract and `TEMPLATES.md` as the canonical templates, using the shapes
  described in this skill and in the `talk-it-through` format docs
  (`DECISIONS-FORMAT.md`, `PROMOTED-MEMORY-FORMAT.md`, `CONTEXT-FORMAT.md`).
- If `memory/index.md` is missing, recreate it from the `TEMPLATES.md` index template before writing promoted memory.
- If `memory/log.md` is missing, recreate it from the `TEMPLATES.md` log template before appending.
- If `TEMPLATES.md` is itself unavailable, do not block: fall back to the
  templates embedded in this skill and the format docs, and recreate
  `TEMPLATES.md` from them.
- Missing personal files are normal, not an error.

## Lint Workflow

Use when asked to review memory health or before broad cleanup.

Run the deterministic index audit first:

`python3 .agents/skills/personal-memory/gate.py --memory memory audit`

It reports promoted files missing from `memory/index.md`, index entries pointing to files that no longer exist, topic-folder problems (a promoted file directly in `workflows/`/`decisions/`, a topic folder not in `memory/schema.json`, a sub-index missing a file or drifted from `indexes.py`), and Client Memory problems (missing frontmatter keys, unknown subject, subject/client not matching the folders, note not on its hub, hub out of date, hub without an `index.md` row), and exits non-zero when anything needs fixing. It also prints `crowded` warnings (a memory folder holding more than 15 `.md` files directly) but does not fail on them. Fix hub problems by running `hubs.py`; fix sub-index drift by running `indexes.py`. `memory/candidates/` is not audited. For `gate.py audit` to recognize an index entry, the row must carry the file path either backticked (`` `memory/decisions/<topic>/decision-x.md` ``) or as a markdown link (`[title](memory/decisions/<topic>/decision-x.md)`).

Then also check for:

- Index rows pointing to missing files.
- Promoted files missing from `memory/index.md`.
- Empty promoted topic files.
- Conflicting active promoted rules.
- Cross-links pointing to memory files that do not exist (report only — broken links are tolerated, not auto-removed).

Report findings before making broad changes. Safe deterministic fixes include removing stale rows and adding missing index rows for existing files.

Note on `gate.py`: it provides a single `audit` command that checks `memory/index.md` against the promoted files and Client Memory on disk. It checks structure only; it does not check whether a memory item is true (see the grounding rule in Capture Workflow).

## Review Cadence

If promoted memory is relevant to the current task and older than 90 days (check `updated`), re-ground it against current tool output or files before relying on it. If it is stale, update it in place or supersede it per Conflict Resolution. Do not ask the user.

## Prune and Supersede

- When a promoted preference changes, update the promoted topic file and record prior rule in notes as superseded.
- If promoted memory is wrong or no longer useful, delete it and remove its index references (record the removal in `memory/log.md`).
- Exception: Procedures are corrected in place (git is the history), never superseded in Notes.

## Output Rules

- After capturing, end the reply with one line per item: `Memory saved: <path> - <short summary>`.
- Mention any automatic omission in one line, without echoing the omitted content (for example, `Omitted: credential in tool output`).
- If nothing qualified at wrap-up, say `Memory check: nothing worth capturing.`
- Keep memory notes short and operational.
