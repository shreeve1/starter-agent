# Personal Memory

This directory is a local, personal memory area for sessions in this workspace.

Populated memory `.md` files are tracked in this workspace's local git repo. Keep the repo without a remote and never push. Shipped hooks are disabled in this Codex workspace; run the memory audit directly before committing. Never store credentials. Binaries and `raw/` stay git-ignored.


## Purpose

Use `memory/` to preserve durable non-code preferences and useful working context, including:

- Assistant response preferences.
- Email and voice communication preferences.
- Important docs, links, or paths to remember.
- Redacted reusable Ticket Guides for future ticket research.
- Workflow habits and approval preferences.
- Repeated corrections that should become future defaults.
- Decisions deliberately finalized by decision-capture workflows.
- Lasting client facts (Client Memory).

## Safety

- Do not store secrets, tokens, passwords, API keys, bearer strings, OAuth credentials, or credential-like config. Omit them automatically; never ask.
- Client and third-party information (names, environments, contacts, config facts) is allowed in summaries. Exception: Ticket Guides in `guides/` stay redacted.
- Prefer summaries over raw content.
- Store raw snippets only when explicitly requested, with credentials stripped.
- Keep memory local: commit to the local repo only; never add a remote or push it.

## Data Classes

- `shareable-scaffold`: templates, rules, and empty placeholders.
- `personal-summary`: locally tracked summaries of preferences, docs, workflows, communication style, and client facts.
- `raw-private`: git-ignored raw snippets and binaries, saved only with explicit approval.

├── decisions/<topic>/   # topics below; index.md generated by indexes.py
├── clients/       # Client Memory: clients/<subject>/<short>/<slug>.md

## Capture

There are no candidates and no approval step, except for Procedures: a shared one in `workflows/<area>/` is saved only through an owner-approved change. At the end of each task, when a capture trigger fired (a correction, a stated rule/preference, a described workflow/boundary, a settled decision, or a reusable fact discovered while working) and the item is not a one-off detail or work still in motion, the agent writes it to the proper topic file itself (workflows and decisions go into a topic folder from the `topics` list in `memory/schema.json`; lasting client facts go to Client Memory, then `hubs.py`), updates `index.md` and `log.md`, runs `python3 .agents/skills/personal-memory/indexes.py` for workflow/decision changes and `gate.py audit`, and reports what it saved. Credentials are omitted automatically.

Not memory: `clients/<short>/tickets/`, `clients/<short>/projects/`, `clients/<short>/meetings/` and `clients/<short>/procedures/` (workspace root) are documents about one ticket, project, meeting or client workflow. The one-off / work-in-motion exclusion does not apply to them; write them freely. Lasting facts learned there are copied into Client Memory.


Workflows that finalize durable knowledge with the user in the loop, such as `talk-it-through`, promote settled items directly to their proper topic file at wrap-up.

## Client Memory

Lasting facts about a client go to `memory/clients/<subject>/<short>/<slug>.md`, one fact per note (template in `TEMPLATES.md`). `<short>` is the Client Short Name from `glossary.md`. Subjects come from the `client_subjects` list in `memory/schema.json` — the source of truth. An agent adds a subject only with the owner's approval, and `gate.py audit` fails any note whose subject is not in the schema. What a subject holds, e.g.: `halo` — the client's ticket system setup (client ID, contracts, ticket habits, sites); `365` — Microsoft 365 / Entra / Exchange tenant facts; `temperature` — dated, sourced observations of what pleases or frustrates the client, the carve-out from the "no guesses about personality" capture rule: an observed reaction with a date and a source is allowed; a character judgement is not.

A fact that spans subjects is filed where a task would look first and linked from a note in the other subject. Every note carries `type: client-memory`, `client`, `subject`, `title`, `verified` (date last confirmed) and `source` (ticket number, "the owner said", or meeting id).

After writing notes, run `python3 .agents/skills/personal-memory/hubs.py`. It regenerates `memory/clients/_hubs/<short>.md`, one hub per client listing every note by subject plus that client's `clients/<short>/tickets/`, `projects/` and `procedures/` files. Hubs are never hand-edited. Each hub has one row in `index.md`. Client skills read a client's memory through its hub.

## Naming

Use lowercase hyphenated slugs. Default promoted topic files:

- `memory/preferences/assistant-style.md`
- `memory/email/tone-and-format.md`
- `memory/voice/voice-mode.md`
- `memory/docs/important-docs.md`
- `memory/workflows/<topic>/<slug>.md` (e.g. `memory/workflows/memory/session-end.md`)

Workflows and decisions live in topic folders, picked from the `topics` list in `memory/schema.json` (a new topic only with the owner's OK). No promoted file sits directly in `workflows/` or `decisions/`. Shared Procedures live in `workflows/<area>/` too; they are corrected in place (git is the history), so the superseded/`Retired` rule does not apply to them. After writing one, run `python3 .agents/skills/personal-memory/indexes.py` (regenerates `memory/workflows/index.md` / `memory/decisions/index.md`, grouping by topic with superseded files under `Retired`) and `gate.py audit`. 15-file rule: a memory folder holding more than 15 `.md` files directly gets topic subfolders plus a generated index; `gate.py crowded` reports it.

Decision-capture workflows may create promoted decision files under `memory/decisions/<topic>/` using `decision-<slug>.md`.

Ticket Guides use flat, searchable filenames under `memory/guides/`, for example `m365-shared-mailbox-send-as-failure.md`.

The entity directory is a single root file `memory/glossary.md` (sections People / Acronyms / Codenames) — shorthand -> full identity. It is distinct from `CONTEXT.md`: glossary answers "who/what is this?", CONTEXT.md answers "which meaning?". Contested/overloaded terms go to `CONTEXT.md`; plain label expansions go to the glossary.

## Session-End Check

Before finishing a meaningful session, agents capture what qualifies, then report what was saved.

If nothing qualifies, say: `Memory check: nothing worth capturing.`

## Cross-linking

- Memory topics may link to each other with standard markdown links using workspace-relative paths that start with `memory/`, for example `[email tone](memory/email/tone-and-format.md)` — the same base `memory/index.md` uses.
- A link expresses a relationship; the relationship kind lives in the prose, not the link.
- Backlinks ("Cited by") are not stored; compute them at read time by reversing the link graph when useful.

## Tolerant Reads

Consume memory permissively. Never refuse to use a memory file because of missing optional frontmatter fields, an unknown `type`, extra unrecognized keys, a missing `index.md`, or a broken cross-link. Do best-effort consumption; a broken link may just be not-yet-written memory.

## Maintenance

- Recreate missing `memory/index.md` or `memory/log.md` when first needed.
- Before writing memory, check existing topic files for a match and update in place instead of duplicating.
- If a new item conflicts with existing promoted memory, supersede it: make the new rule active and record the old one in Notes as superseded with the date. Procedures are the exception: corrected in place, git is the history.
- If a promoted memory item is relevant and older than 90 days, re-ground it against current tool output or files before relying on it; update or supersede it if stale.
